Linux incident response

Collect volatile facts first and keep an evidence trail.

Guidebook homeEvidence folders
If the system may contain evidence of a serious crime, regulated data, or an active business incident, follow the organization's response plan and contact the responsible incident lead before changing it.

Choose containment deliberately

Disconnecting a host can stop harm but can also destroy remote-session and memory evidence. Do not improvise. Record who authorized containment, what was disconnected, and the exact time.

Collect volatile host facts

date -Is
hostnamectl
ip -brief address
ip route
ss -tulpn
ps auxf
who
last -F | head -50
systemctl --failed
journalctl --since "2 hours ago" --no-pager

Redirect output into a case directory when policy permits. Avoid installing new software on the affected disk; doing so changes evidence.

Preserve files with checksums

sha256sum suspicious-file.bin | tee suspicious-file.bin.sha256
stat suspicious-file.bin | tee suspicious-file.bin.stat.txt
file suspicious-file.bin | tee suspicious-file.bin.type.txt

Work from a copy when possible. Record source path, collector, timestamp, checksum, destination, and every transfer.

Look for high-signal changes

  • Unexpected listening services or outbound connections
  • New accounts, SSH keys, scheduled jobs, or enabled services
  • Authentication failures followed by successful logins
  • Executable files in temporary or user-writable directories
  • Security controls disabled near the start of the incident

Finish with recovery and lessons

Prefer rebuilding from trusted media over attempting to clean an unknown compromise in place. Rotate exposed secrets, patch the entry point, monitor for recurrence, and write down which preventive or detective control should change.
